# Supabase 安裝與升級

網站只公開 publishable／anon key 與課堂加入碼，管理員密碼不放在前端。課堂資料留在私有 `pi_helper` schema，公開 RPC 會核對管理員／個人帳號密碼或學生工作階段。

## 新專案

1. 在 Supabase SQL Editor 執行 [完整安裝檔](../supabase/install.sql)。
2. 執行 [建立課堂](../supabase/create-classroom.sql) **一次**，私下保存回傳的管理員密碼；預設期限為建立後 30 天。
3. 在 [config.js](../config.js) 填寫 Project URL、公開 publishable／anon key，以及學生課堂碼。
4. 用管理員密碼登入工作台，在課堂設定確認組數、課堂開關、期限及教材，再設定個人帳號。

## 既有專案

先備份，再執行同一份 `supabase/install.sql`。不要執行建立課堂檔，也不用修改原課堂碼或密碼。

首次導入安裝紀錄的既有專案會在**同一個交易**中依序套用所有來源，最後恢復最新版帳號與課堂函式，保留既有資料。後續重跑時只執行缺少的 migration。錯誤會回滾整批，避免停在中途的舊版函式。

安裝後重新整理網站，驗證管理員／個人帳號登入、求助接手、清除看板、老師指定步驟與暫停／恢復。安裝本身不會清除紀錄，也不建立額外課堂。

## 版本與維護

來源統一放在 `supabase/migrations/`，以 001～013 排序。`supabase/install.sql` 由 `node scripts/build-sql.cjs` 產生；在 SQL Editor 使用這份安裝檔，不要挑選舊來源重跑。

`pi_helper.schema_migrations` 記錄檔名、版本、SHA-256 與執行時間，開啟 RLS，匿名使用者不可讀寫。已完成的版本會跳過；校驗碼不符、歷史有缺口或安裝檔比資料庫舊時拒絕執行。安裝期間以交易鎖避免兩人同時升級。

後續變更新增下一個連續編號 SQL，保留 `begin;`／`commit;` 外框，然後重新產生 installer。不要修改已發布 migration；CI 會檢查 bundle 是否和來源一致。若資料庫已經記錄過某版，直接修改該來源會讓檢查失敗，應以新 migration 修正。

建課檔是管理操作，不是 migration，每次執行都會建立一堂新課。健康檢查來源為 `012_health_check.sql`，僅回傳 true，不存取課堂資料。

`013_device_monitor.sql` 新增設備回報；完成 SQL 升級後仍需在各組 Pi 安裝回報程式。工作台的「課堂設定 → 樹莓派設備回報」提供配對與安裝入口，詳見 [設備回報說明](DEVICE_MONITOR.md)。這不會自動替學生確認課程完成。

## 帳號與組別

- 組數可設 1～99；減少組數不刪掉舊回報。
- 原管理員密碼保留；管理員可建立、修改或停用最多 50 個個人登入帳號。
- 每人以自己的密碼登入。其他帳號可修改自己，無法管理別人。
- 密碼須非空、不重複，無長度限制；完整內容先 SHA-256 再 bcrypt，避免長密碼遭截斷。
- 網站不把管理密碼放在網址或瀏覽器儲存空間；接手稱呼由伺服器驗證身分後帶入。

## 驗證界線

`tests/run-install-sql.cjs` 在隔離資料庫驗證新安裝、建課語法、重跑、既有專案導入與校驗碼拒絕。其他 SQL／瀏覽器測試見 [README](../README.md)。本次整理未執行正式課堂 SQL；需要 Supabase 專案管理員依上方步驟部署。
